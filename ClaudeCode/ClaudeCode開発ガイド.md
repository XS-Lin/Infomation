# ストーリーで覚えるClaude Code開発ガイド #

## 設定サンプル ##

### 1.コードベース探索 ###

1. リポジトリの全体構造を把握する

~~~txt
リポジトリの全体構造を分析してください。 以下の観点で整理してほしいです: 
- ディレクトリ構成と各ディレクトリの役割 
- 主要な技術スタック（言語、フレームワーク、ライブラリ） 
- エントリーポイント（アプリケーションの起動箇所） 
- 設定ファイルの一覧と概要
~~~

1. 特定の機能の実装箇所を探す

~~~txt
ユーザー認証（ログイン・ログアウト・セッション管理）に関連する 実装箇所をすべてリストアップしてください。 
- 認証ロジックのコアファイル 
- ミドルウェアやガード 
- 認証に関連するAPIルート 
- 認証設定（トークンの有効期限など） それぞれファイルパスと該当行番号を示してください。
~~~

1. データフローを追跡する

~~~txt
/api/orders エンドポイントのデータフローを追跡してください。 リクエストを受け取ってからレスポンスを返すまでの処理を、 以下の順序で説明してほしいです: 
1. ルーティング（どのファイルで受け取るか） 
2. バリデーション（入力チェック） 
3. ビジネスロジック（注文処理の本体） 
4. データベースへの書き込み 
5. レスポンスの組み立て 各ステップでファイルパスと関数名を明示してください。
~~~

### 2.デバッグ・修正 ###

1. スタックトレースから原因を特定する

~~~txt
以下のスタックトレースの原因を分析してください。
- 該当ファイルのコードを読んで、原因を特定
- どのような入力データのときにこのエラーが起きるか
- 根本原因（バリエーション不足？型の不整合？）を教えてください
~~~

1. 修正案を生成してもらう

~~~txt
- userオブジェクトがundefinedの場合のガード処理を追加
- 既存のテストが壊れないようにする
- 修正箇所は最小限に留める
~~~

1. 修正後のテストを実行して検証する

~~~txt
1. まず既存テストの実行
2. テストが失敗した場合は原因を分析
3. 今回の修正（undefinedガード）をカバーするテストケースを追加
4. 全テストが通ることを確認
テスト結果をステップごとに報告してください。
~~~

### 3.CLAUDE.md テンプレート ###

1. 個人用CLAUDE.md

~~~txt
#CLAUDE.md 

## プロジェクト概要 
- プロジェクト名: [プロジェクト名] 
- 概要: [一文で説明] 
- 技術スタック: [言語], [フレームワーク], [DB] 

## ディレクトリ構成 
- src/ — アプリケーションコード 
- tests/ — テストコード 
- docs/ — ドキュメント 

## 開発コマンド 
- ビルド: `npm run build` 
- テスト: `npm test` 
- lint: `npm run lint` 
- 開発サーバー: `npm run dev` 

## コーディングルール 
- 変数名・関数名はキャメルケース 
- コメントは日本語で記述 
- 関数には必ずJSDocコメントを付ける 

## 注意事項 
- .envファイルは絶対にコミットしない 
- mainブランチへの直接プッシュは禁止
~~~

1. チーム用CLAUDE.md

~~~txt
#CLAUDE.md — チーム開発ガイドライン 

## プロジェクト概要 
- サービス名: [サービス名] 
- アーキテクチャ: クリーンアーキテクチャ（4層構造） 
- 言語: TypeScript (strict mode) 
- フレームワーク: NestJS 
- DB: PostgreSQL + Prisma ORM 
- テスト: Jest + Supertest 

## アーキテクチャ方針 
- レイヤー構造: Controller → Service → Repository → Entity 
- 依存の方向は内側のみ（Controller が Repository を直接呼ばない） 
- ビジネスロジックは必ず Service 層に置く 
- Controller はリクエストの受け取りとレスポンスの返却のみ 

## コーディング規約 
- 命名規則: キャメルケース（変数・関数）、パスカルケース（クラス・型） 
- ファイル命名: ケバブケース（user-profile.service.ts） 
- インポート順序: 外部モジュール → 内部モジュール → 相対パス 
- 1ファイル1クラスを原則とする 
- any型の使用は禁止（型安全を最優先） 
- マジックナンバー禁止（定数として定義する） 

## 禁止事項 
- console.log によるデバッグ出力をコミットしない 
- eslint-disable コメントを追加しない（ルール側を修正する） 
- テストのない機能追加をしない 
- 既存のAPIレスポンス形式を無断で変更しない 
- node_modules/ や dist/ をコミットしない 

## テスト規約 
- ユニットテスト: 全Serviceクラスに必須 
- テストファイル配置: 対象ファイルと同じディレクトリに *.spec.ts 
- モック: 外部依存（DB、API）は必ずモック化 
- カバレッジ目標: ライン80%以上 
- テスト実行: `npm test`（全件）、 `npm test -- --watch`（開発中） 

## Git規約 
- ブランチ命名: feature/[チケット番号]-[概要] 
- コミットメッセージ: Conventional Commits 形式 
- feat: 新機能、fix: バグ修正、refactor: リファクタリング 
- PRはレビュー1名以上の承認で マージ可
~~~

### 5.リファクタリング・Git操作 ###

1. 影響範囲を分析する

~~~txt
xx をリファクタリングしたい。
変更前に影響範囲を分析してください。
- この関数を直接呼び出しているファイルの一覧
- 間接的に依存しているモジュール（呼び出し元の呼び出し元）
- この関数の戻り値の型に依存しているコード
- 関連するテストファイル
- 変更時のリスク評価（高・中・低）
まだ変更は行わないでください。分析結果だけ報告してください。
~~~

1. 段階的リファクタリングを実行する

~~~txt
以下の方針で段階的に進めてください:
1. まず現在の責務を分類して報告（認証/プロフィール/通知など）
2. 各ステップで1つの責務だけを別クラスに切り出す
3. 各ステップの後にテストを実行して既存機能が壊れていないか確認
4. 全ステップ完了後に最終的なテストを実行
ステップ1の分類結果を見せてから、次に進んでください。
~~~

1. git worktreeで並行作業する

~~~txt
git worktreeで並行作業環境を構築してください。
1. 現在の作業ブランチはそのまま維持 
2. 新しいworktreeを作成
3. hotfixブランチの作業ディレクトリに移動して状況を確認
4. 修正を実施
~~~

### 6.Skills(カスタムコマンド)テンプレート ###

~~~txt
コードレビューを実施してください。 

## レビュー観点 
1. **バグリスク**: null参照、境界値、型の不整合 
2. **セキュリティ**: SQLインジェクション、XSS、認証漏れ 
3. **パフォーマンス**: N+1クエリ、不要なループ、メモリリーク 
4. **可読性**: 命名、関数の長さ、コメントの適切さ 
5. **テスト**: テストの有無、カバレッジの十分さ 

## 出力形式 各指摘を以下の形式で報告: 
- **[重要度: 高/中/低]** ファイル名:行番号 
- 問題の説明 
- 修正案 

最後にレビュー全体のサマリーを3行で。 
~~~

1. テスト生成用Skills

~~~txt
指定されたファイルのユニットテストを生成してください。 

## テスト方針 - テストフレームワーク: Jest 
- ファイル配置: 対象ファイルと同階層に *.spec.ts 
- モック: 外部依存はすべてモック化 
- テストデータ: ファクトリパターンで生成 

## 必須パターン 
- 正常系: 主要なユースケースを網羅 
- 異常系: エラーハンドリングの検証 
- 境界値: 最小値、最大値、空配列、空文字列

## コーディングスタイル
- テスト名は日本語で記述（例："正常な入力で計算結果を返す"）
- AAAパターン（Arrange-Act-Assert）を遵守
- 各テストは独立して実行可能にする
~~~

1. 引数付きSkillsの例

~~~txt
$ARGUMENTS のコードを解説してください。 

## 解説の観点 
1. **目的**: このコードは何を実現しているか 
2. **仕組み**: 主要な処理フローをステップごとに説明 
3. **依存関係**: 他のモジュールとの関係 
4. **注意点**: 変更時に気をつけるべきこと 

## 出力形式 
- 初心者にも分かるように平易な日本語で 
- 技術用語には簡単な補足を添える 
- コードの該当箇所を引用しながら説明
~~~

使い方: /explain src/services/payment.service.ts のように、 $ARGUMENTS に渡す引数を添えて呼び出します。ファイルパスだけでなく、/explain 認証フロー全体 のように概念を指定することもできます。
